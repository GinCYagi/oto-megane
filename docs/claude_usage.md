# Claude の機能の使い方の記録

音めがねは Claude Code で作っています。目的に合う機能を選び、使った理由・見送った理由をここに残します。

## 2026-11-02 最初の一歩（ページ・試しの音・ファイル・マイク）

### 使ったもの

| 機能 | 何に使ったか | 理由 |
|---|---|---|
| プランモード | コードを書く前に、作るもの・確かめ方・使う機能を計画にして Gin に見せ、了承を得た | 作者（Gin）の考えた一歩目と、Claude の作り方がずれないようにするため |
| 自作のサブエージェント `visual-safety-checker`（`.claude/agents/`） | 画面の点検係。点滅・急な明るさの変化・色だけに乗った意味・コントラスト比・色の見え方の違い（P/D/T 型）・医療の効き目を思わせる言葉を点検し、報告だけする | 画面を作った本人は自分の癖に気づきにくい。別の目で、毎回同じ項目を点検できるようにするため。描き方の決まりが生まれるこの一歩で作った |
| Chrome の見えないモードを CDP で動かす小さな台本（作業用のフォルダに置き、リポジトリには入れていない） | ボタンを押した後の画面を写し、Claude が自分の目で確かめた | 「描けたはず」で終えず、実際の画面を見て直すため。これで試しの音の線の太さの差が小さすぎることに気づき、直した |

### このときに分かったこと

- 新しく作った `.claude/agents/` の定義は、同じセッションの中では呼べなかった（「Agent type 'visual-safety-checker' not found」）。公式の説明では、Claude Code が見張るのはセッション開始のときにあったフォルダだけで、新しく `agents` フォルダを作ったときは再起動が要る（https://code.claude.com/docs/en/sub-agents 、2026-11-02 確認）。今回は、汎用のサブエージェントに同じ定義ファイルを読ませて従わせた。次のセッションからは名前で呼べる。

### 点検係の指摘と、直したこと（2026-11-02）

点検係は 6 項目のうち、色の見え方の違い（P/D/T 型）と言葉は「問題なし」、画面全体の光りも「問題なし」とした。直したのは次のとおり。

| 指摘 | 直したこと |
|---|---|
| 「静か」と「音あり」が、しきい値の前後で毎コマ入れ替わりうる（字のちらつき） | 入るのは +8 dB、戻るのは +5 dB と幅を変え、戻るのは 0.4 秒続いてからにした。字は状態が変わったときだけ書き換える（読み上げも騒がしくしない） |
| 「いま」の線（2.3:1）と枠・斜線（2.1:1）が暗い | どちらも #8b9098（地に対して約 5.5:1） |
| 帯の境とオクターブの線が並び、見分けにくい | 帯の境を点線にした |
| 「止める」が押せないことを暗さだけで伝えていた | いつも押せる形にした（止まっているときに押しても何も起きない） |
| 帯の柱の間に縦の筋が出る | 柱の位置を整数の画素にそろえた |

そのままにしたもの：オクターブの目盛り線は、わざと控えめにしている（1.3:1）。実機のまぶしさは、点検係も確かめられないので、Gin の目で確かめる。

### 見送ったもの

| 機能 | 理由 |
|---|---|
| Explore・Plan のサブエージェント | リポジトリにまだ README しかなく、読むものが少なかったため。計画は自分で書けた |
| フック（音・絵のファイルを git に入れる前に出どころを確かめる） | 今回は音のファイルをリポジトリに入れない（端末の中のファイルを選ぶ形と、コードで合成した試しの音だけ）。素材を入れる段で作る |
| スキル | 決まった手順がまだ繰り返し出てきていないため |
| `/code-review` | まとまった差分ができてから使う |

## 2026-11-03 曲を見る（曲＋歌声だけの音）・大きさと拍

### 使ったもの

| 機能 | 何に使ったか | 理由 |
|---|---|---|
| 実機の動画とスクリーンショットを読む | Gin が OnePlus 6 で撮った動画から、ffmpeg で 4 秒おきのコマを一覧にして見た。動画の音を、ページと同じ関数に通して数えた | 「線にならない」を見た目の印象で終えず、何 % のコマで高さを読めたかの数で原因を確かめるため（[design_notes.md](design_notes.md)） |
| 見えない Chrome を CDP で動かす台本（前日のものを広げた） | ファイル選択に Gin の歌のファイルを入れて鳴らし、20 秒・45 秒の画面を写した | 実際の曲で線や拍がどう見えるかを、Claude が自分の目で確かめるため。これで「数珠つなぎの線」と「明るすぎる面」に気づいて直した |
| 点検係（`visual-safety-checker` の定義を読ませた汎用のサブエージェント、2 回目） | 新しい見せ方（大きさの面・拍の線・曲の欄）を点検した | 前回と同じ項目で、作った本人と別の目で見るため |

### 点検係の指摘と、直したこと

| 指摘 | 直したこと |
|---|---|
| 拍の印が 1 秒に 5 回まで出る（WCAG 2.3.2 の 3 回を超える） | 1 秒に 3 回までにした |
| 拍の線を、次の柱が上から塗り、面の中で細く切れる | 面をすべて塗ってから、拍の線をまとめて描くようにした |
| 大きさの面と地の明るさの比が 2.82（図形の目安 3:1 に届かない） | #61666e にして 3.05 にした |
| 説明の文で、「いま」の線と拍の線をどちらも「縦線」と呼んでいる | 「右寄りの動かない灰色の縦線」「右から流れてくる明るい線」と、形と動きで書き分けた |
| 「曲を鳴らす」の結果が欄の外にしか出ず、押しても何も起きないように見える | 欄の中にも知らせを出し、鳴り始めたら描く枠まで画面を送るようにした |
| キーボードで動かすと、焦点の枠がボタンではなくファイル名の字に付く | ボタンの側に付けた |

確かめられなかったこと（点検係も同じ）：実機の暗い部屋でのまぶしさ、拍が曲の拍子と合っているか。どちらも Gin の目と耳で確かめる。

## 2026-11-03 歌モードの楽譜と、春の小川の書き起こし

### 使ったもの

| 機能 | 何に使ったか | 理由 |
|---|---|---|
| 汎用のサブエージェント（書き起こし係） | 1935 年の本の春の小川のページ画像（パブリックドメイン）を拡大して読み、旋律・詞・右手・左手・強弱・構成を楽譜のテキストに起こした | 画像を細かく切って何十枚も見る仕事で、量が多い。そのあいだに、Claude 本体は楽譜の書き方の広げ（伴奏・和音・強弱・構成）と仕様書の直しを並行して進めた。頼むときに「鉛筆の書き込みは使わない」「読めない所は推測で埋めず一覧にする」を決まりとして渡した |
| Claude 本体による照らし合わせ | 書き起こしを楽譜の読み込みに通し（小節の長さ・詞と音の数）、作業係が「確信が持てない」とした所の一つ（小節をまたぐタイ）を、自分でも画像で見て確かめた | 作業係の報告は、作業係自身の判断。うのみにせず、機械で確かめられる所は読み込みで、目で見る所は自分で見るため |
| MIDI の書き出し（`tools/score2midi.mjs`） | 書き起こしを、作者が耳で確かめられる形にした | 書き起こしの正しさを最後に確かめられるのは、楽譜を聞いて分かる作者の耳だけのため |
| Claude 本体の書き起こしと、使い捨ての計り（ふるさと） | 1933 年の本のふるさとのページ（4 段・16 小節）を、Claude 本体が読んだ。五線の線の位置を画素で測り、黒い玉の重心から高さを計算し、線と間の名前を重ねた拡大図で確かめた。計りの台本は作業場に置き、リポジトリには入れていない | 紙が少し傾いていて、目で数えると半音（線と間）を取り違えやすかったため。曲が短く、作業係に頼むより、本体で読んで同じ目で確かめるほうが早かった |

| 指摘 | 直したこと |

| 過ぎた所とこの先の線の明るさの比が 2.69（文字でないものの目安 3:1 に届かない） | この先の線を #767b83 にして、比を約 3.6 にした（地との比は約 4.1） |

## 2026-11-05〜11-07 実機で見つかったことを、見えるようにしてから直す

この 3 日間は、作者（Gin）が iPhone・OnePlus 6 の実機で試し、Claude が直す、をくり返しました。実機で起きることを Claude は直接見られません。そこで、推測で直さず、まず数字や画面で見えるようにしてから直しました（Gin、11/7「推測で直さず、まず見えるようにしてください」）。

### 使ったもの

| 機能 | 何に使ったか | 理由 |
|---|---|---|
| Bash で動かす小さな Python の測り（作業用のフォルダに置き、リポジトリには入れていない） | iPhone の画面収録で伴奏が雑音のように録れた件で、Gin から受け取った録画の音を測った。約 21.3 ミリ秒ごとに途切れ、音があるのは毎回 7〜10 ミリ秒ほどと分かった。`?lat=` や `?sr=` を変えても周期が変わらないことから、区切っているのは画面収録の側と推定し、デモ動画は書き出した WAV を使う方針にした（[docs/demo_video.md](demo_video.md) 3 章） | 「雑音がする」という耳の印象だけでは、原因を絞れない。途切れの周期という数字にすると、音めがねの設定のせいか、収録の側のせいかを分けられる |
| `?debug=1`（実機の画面に状態を出す確かめ用の印。Claude が作った） | 一覧の下に、白黒の自動の決まりの材料と、音の仕組みの記録（作った・resume・state の変化・鳴らし始め など、時刻つき）を出した。曲の画面には、歌詞の行の間（px）、行数・字の大きさ・欄の高さ・画面の大きさ・1 行にするしきい値を出した | iPhone だけで起きることは、Mac の Chrome で通っても直ったとは言えない。Gin が実機の画面の数字を読んで伝えれば、Claude は推測しなくて済む。たとえば、全画面で 1 行になった件は、表示を見て `?minfs=28` で開いていたためと分かり、不具合ではなかった |
| 画像を読む（Gin が送った iPhone の写し） | 写しを読んで、直す場所を決めた | 言葉だけでは伝わりにくい、重なり・切れ・かけらの位置を、Claude が自分の目で確かめるため |
| 見えない Chrome を CDP で動かす台本（画面の大きさ・白黒・動きを減らす設定をまねる） | 横向きのスマホの大きさ（844×320〜411、956×330・415）で、歌詞の字の大きさ・行の間・欄の高さを測り、写しを撮った。白黒は `prefers-contrast`、伴奏の始まりは自動再生の許可をまねた | 実機を何台も持てないので、画面の大きさを変えて数字で比べ、Gin が実機で確かめる前に崩れを見つけるため。1 行と 2 行を切り替える字の大きさのしきい値も、この表を Gin に見せてから決めた |
| WebSearch・WebFetch（公式の資料） | Web Audio の `latencyHint`・`sampleRate`、`navigator.audioSession`、WebKit の不具合の報告、ホーム画面に追加の手順、画面を暗くしない仕組み（Screen Wake Lock）、カラーユニバーサルデザイン推奨配色セット、書体 Zen Maru Gothic の使用許諾、CSS の `ruby-align` を調べ、出典と日付を仕様書・README に書いた | 製品や仕様の話は、Claude の知っていることが古いことがある。その場で公式の資料を読んで確かめるため |
| AskUserQuestion | ふるさとの高さの選び方、見方の一枚を出す長さ、色の明るさの決まりを緩めるか、などを Gin に選んでもらった | 作者が決めることを、Claude が勝手に決めないため |
| `node --test`（テスト） | 白黒の決まり、音の頭の光、間奏・後奏の見出し、歌詞の行の替わり目などをテストにした（11/7 の終わりで 75 件） | 実機での直しをくり返しても、前に直したことが崩れていないかを、毎回すぐ確かめるため |

### 実機の点検の指摘と、直したこと

この 3 日間の点検は、Gin の実機と、試してくれた人の声でした。

| 指摘 | 直したこと |
|---|---|
| 横の画面で、下の行の歌詞のルビが上の行の字に重なる。全画面では下の行が画面の下で切れる（debug の表示で「行の間 -4px」） | 決め打ちの位置（em）をやめ、行ごとにルビのはみ出しまで実際に測って置く形（`UtaLyrics.fit`）にした。Mac の Chrome で 32 通り（高さ 4 つ・ふだんと白黒・debug あり・なし）を測り、行の間 6px 以上を確かめた |
| 端末の「コントラストを上げる」をオンにしても、白黒が自動でオンにならない | 自分で選んだ値を覚え方の決まりと分け、端末の設定と同じ選びは覚えないようにした。決まりの材料を `?debug=1` に出し、Gin が実機で自動の切り替えを確かめた |
| 曲の途中で白黒を替えると、線の画面の色が混ざる | 色を CSS から読み直して描き直すようにした |
| 伴奏が始まらないとき、知らせと「触ると続きから」の札が同時に出て食い違い、知らせが歌詞に重なる | 札を下げて知らせだけにし、知らせは線の段の上の端に出すようにした |
| 間奏・後奏のあいだ、直前の歌詞が出たままで「まだ歌うのか」「止まったのか」が分からない | 「（間奏）」「（後奏）」を出すようにした。括弧は「声に出さない補足」というふだんの文の約束で「ここは歌わない」と伝わる（Gin）。曲が終わって「おしまい」が出たら「（後奏）」は消す |
| ツールバーありの横では、歌詞の 2 行が重ならない代わりに、字がかなり小さくなる | 歌詞の欄の高さを測り、2 行だと字が 24px より小さくなるときだけ、いまの行だけを大きく出すようにした。Gin が iPhone で、全画面は 2 行（27px）、ツールバーありは 1 行（25px）を確かめた |
| 線が左へ流れて端で切れるとき、濁点や点だけが左の端に残り、ごみに見える | 字の左の端が画面の端に着いたら、その字は描かない（着く前の半字ぶんで薄くする）ようにした |

### 見送ったもの

- **点検係（`visual-safety-checker`）とサブエージェント**：この 3 日間は使わなかった。直しは実機の写しと数字から一つずつで、範囲が小さかったため。新しい色・白黒・光がそろったので、T9 の軽い点検（点検係と `/code-review`）で、まとめて別の目で見る。
- **iPhone の画面収録の音**：途切れの原因が収録の側と推定できたので、直そうとせず、デモ動画は WAV を使う。

## 2026-11-07（夜）提出に向けて：実機の数字で直す・手を分ける・人の目で確かめる

前の節の続きです。iPhone の画面収録の音を測って、伴奏が途切れる原因を絞ったことは、前の節の「使ったもの」に書きました。

### 使ったもの

| 機能・やり方 | 何に使ったか | 理由 |
|---|---|---|
| `?debug=1` の数字を読みながら直す（OnePlus 6 の全画面、v=41〜44） | OnePlus 6 の Chrome・全画面で、春の小川の歌詞が画面の下にはみ出した。Gin が debug の「欄の高さ 115px」を読み、Mac の Chrome（91px）と比べて、曲の画面の全体が画面より約 60px 高いと推定して直した（v=41）。ほかのアプリから戻ったときも 115px のままだったので、見えるようになったときに合わせ直すようにした（v=42）。戻ると Android の Chrome が全画面を解除するので、触ったときに全画面に入り直すようにした（v=43）。全画面に戻るのが 1 回目だけだったので、時間の幅で決めるのをやめ、全画面で始めた印で決める形にした。debug には「全画面：入っている／入っていない・戻す予定 あり／なし」を出した（v=44）。v=44 で Gin が OnePlus 6 で 2 回試し、2 回とも全画面に戻った（縦にして横に戻した場合も含む） | Mac の Chrome では再現しなかった。実機の数字があれば、推測を一つずつ確かめながら直せる。直ったかどうかも、同じ表示で Gin が見て分かる |
| 見えない Chrome で、実機の起き方をまねる | 「resize の知らせを受け取れない端末」と「全画面の解除から 3 秒たって裏へ回る」を台本でまねた。直す前に Gin の見た形が出ること、直したあとに消えることを確かめた | 実機を手元で動かせないので、Gin の見立てどおりの順番を再現してから直すため |
| 別のセッションの Claude（相談役）と手を分ける | 相談役の Claude が Gin と話して、何を直すか・どんな文にするかを決め、指示の文にした。このセッションは、それを受けて作って確かめ、push して 3 行で報告した | 判断と実装を分けると、一つの会話が長くなりすぎない。決めた理由と作った中身を、別々に確かめられる |
